# Deploying recall to AWS

Without an argument, decide from the request: deploy it, diagnose the last run, grep the logs, or
smoke-test what is live. `--help` means summarise the sections below and stop.

## The one constraint that shapes everything

The target account is **236058984017** (`us-east-1`). Its console session is the **root user**: there
are no IAM users, so no access keys, and CloudShell refuses to run as root.

**The local `aws` CLI cannot reach that account.** Any local AWS credentials belong to a different
account. So:

- deploys go through the GitHub workflow, never `./deploy.sh` from a laptop;
- anything that needs to be read from AWS is read through the web console with the Chrome tools.

`aws` commands that hit *public* resources still work from anywhere — see the layer-version trick
below.

## Deploy

```bash
gh workflow run deploy.yml --ref main
gh run watch <run-id> --exit-status
```

The workflow is `.github/workflows/deploy.yml`: `workflow_dispatch` only, `concurrency: deploy`,
OIDC via `aws-actions/configure-aws-credentials`. It runs `ruff` + `pytest`, then `./deploy.sh`,
which builds the arm64/py3.13 Lambda package, deploys `backend/template.yaml` and uploads the Vite
bundle to S3 behind CloudFront.

A green run ends with:

```
App: https://<distribution>.cloudfront.net
API: https://<id>.lambda-url.us-east-1.on.aws/
```

## Diagnose a red run

Start here, always:

```bash
gh run view <run-id> --log-failed | grep -vE "Uploading to" | tail -25
```

When the stack itself is what failed, the `Why the stack failed` step already printed the
`CREATE_FAILED` / `UPDATE_FAILED` events with their reasons — read those before touching anything.

### Failures this stack has already hit

| Log line | Real cause | Fix |
|---|---|---|
| `Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity` | GitHub mints the `sub` claim with **immutable IDs** (`repo:owner@12966514/repo@1306083059:ref:...`), not with names | update `GitHubSubject` on the `recall-github-oidc` stack — see `recall-bootstrap-aws` |
| `ruff` fails in CI but passes locally | `ruff` was unpinned and every minor release widens the default rule set | it is pinned to `0.15.22` in the workflow; if you bump it, run it locally first |
| `lambda:GetLayerVersion ... because no resource-based policy allows` | the Lambda Web Adapter layer version in the template does not exist | find a real one (below) and update `template.yaml` |
| `Specified ReservedConcurrentExecutions ... below its minimum value of [10]` | new accounts get a concurrency quota of 10, so reserving any of it breaks the floor | do not reserve concurrency, or raise the quota in Service Quotas |
| `Stack ... is in ROLLBACK_COMPLETE state and can not be updated` | a first creation that failed leaves an unusable stack | already handled: `deploy.sh` deletes it and waits before retrying |
| `psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec` | **not the cause** — the pool retries in a background thread, so the caller only ever sees the timeout | grep CloudWatch for `connecting` to get libpq's real error |

### Is a public Lambda layer version real?

A public layer answers from *any* account, so local credentials are enough:

```bash
aws lambda get-layer-version-by-arn \
  --arn arn:aws:lambda:us-east-1:753240598075:layer:LambdaAdapterLayerArm64:<n> \
  --region us-east-1 --query Version --output text
```

`AccessDeniedException ... no resource-based policy allows` means that version does not exist. Walk
`<n>` upwards until it stops answering; the last one that answers is current. As of 2026-07 that is
**29** (LWA 1.1.0), which is what `backend/template.yaml` pins.

## Read the Lambda logs

Needs the Chrome tools — load them first (see the `claude-in-chrome` skill).

The log group is `/aws/lambda/recall-ApiFunction-*`; the suffix is generated by CloudFormation and
changes whenever the function is recreated, so **look it up, never hardcode it**:

```
https://us-east-1.console.aws.amazon.com/cloudwatch/home?region=us-east-1#logsV2:log-groups
```

Then filter the whole group by pattern, which is far faster than opening a stream:

```
.../log-groups/log-group/$252Faws$252Flambda$252F<log-group>/log-events$3FfilterPattern$3D$2522connecting$2522
```

Two traps:

- The event list pages from the **oldest** match, and scrolling does not reach the newest. To see
  what just happened, filter on a string unique to the new error rather than scrolling.
- Opening a single log stream sometimes renders `Unable to load content`. Navigating to the same URL
  a second time usually works.

## Verify what is live

```bash
API=$(gh run view <run-id> --log | grep -o 'https://[a-z0-9]*\.lambda-url[^ ]*' | tail -1)
curl -s -o /dev/null -w "%{http_code}\n" "$API/health"    # 200
curl -s "$API/tickets" | head -c 200                       # rows, not 500
curl -s -X POST "$API/tickets/<uuid>/handle" --max-time 300 | head -c 400
```

The `handle` call is the only real end-to-end test: it exercises CockroachDB and the LLM together.
A good response carries `root_cause`, `confidence` and a `most_relevant_incident`.

`"via": "fallback"` in the evidence is **expected** — the Cockroach MCP does not answer from Lambda
and `memory._read()` falls back to psycopg, which is exactly the designed behaviour.

## TLS to CockroachDB — do not regress this

The CA travels inside the package: `backend/certs/cockroach-root.crt` (ISRG Root X1), copied by
`deploy.sh`, pointed at by `PGSSLROOTCERT: /var/task/certs/cockroach-root.crt` in the template.

Do **not** replace it with `sslrootcert=system` in `DATABASE_URL`. The OpenSSL baked into the
`psycopg[binary]` wheel carries its own OPENSSLDIR from build time, which exists neither on Lambda
nor on macOS, so `system` resolves no trust store at all and the handshake fails with
`certificate verify failed`. Also note a URL parameter beats the `PGSSLROOTCERT` environment
variable, so leaving `sslrootcert=` in the secret silently disables the packaged CA.
